# Лабораторная работа №2 — чтение информации из графических файлов

## Цель работы

Цель лабораторной работы — изучить устройство растровых графических форматов и научиться самостоятельно получать основные характеристики изображения непосредственно из бинарной структуры файла.

Веб-приложение считывает метаданные изображений форматов **JPG/JPEG, GIF, TIFF, BMP, PNG и PCX**. Проект выполнен с учетом требований группы **10А**: сторонние библиотеки для чтения метаданных не используются. Каждый файл открывается как набор байтов, после чего нужная информация извлекается вручную по сигнатурам, заголовкам, чанкам, маркерам и TIFF IFD.

## Что было реализовано

Приложение позволяет выбрать папку с изображениями и получить для каждого файла:

- имя файла;
- фактический формат;
- размеры изображения в пикселях;
- разрешение DPI;
- глубину цвета;
- тип сжатия;
- размер файла;
- статус целостности;
- дополнительные параметры, зависящие от формата.

Формат определяется по содержимому файла, а не только по расширению. Поэтому, например, PNG-файл, переименованный в `.jpg`, будет распознан как PNG и отмечен как файл с несовпадающим расширением.

Для работы с большими папками реализованы частичное чтение файлов, пул Web Worker, индикатор прогресса и виртуализированная таблица. Файл не загружается полностью в память, если для чтения метаданных достаточно отдельных участков заголовка или данных по известным смещениям.

Также реализована проверка поврежденных файлов: приложение обрабатывает ошибку конкретного изображения и продолжает работу с остальными файлами.

## Как выполнялось чтение данных

Общий принцип для всех форматов одинаков:

1. Файл определяется по его сигнатуре или Magic Number.
2. Через `Blob.slice()` читается только необходимый диапазон байтов.
3. Байты преобразуются в `Uint8Array` или читаются через `DataView`.
4. Парсер конкретного формата вручную разбирает его структуру.
5. Полученные значения приводятся к единому объекту результата.
6. Результат передается из Web Worker в основной поток и отображается в таблице.

Для получения метаданных не используются `Image`, `canvas`, PIL, System.Drawing, ExifReader и другие готовые средства чтения свойств изображений.

## Как пользоваться приложением

1. Открыть приложение в браузере.
2. Нажать кнопку выбора папки.
3. Выбрать папку с изображениями.
4. Дождаться окончания обработки — состояние показывается progress bar.
5. Просмотреть результаты в таблице.
6. При необходимости открыть подробную информацию по конкретному файлу.

Поддерживаемые форматы:

- JPG / JPEG;
- PNG;
- GIF;
- TIFF / TIF;
- BMP;
- PCX.

## Архитектура

Проект разделен на три слоя.

### 1. Presentation Layer — `src/presentation/`

Отвечает только за интерфейс.

- `app.js` — выбор папки, фильтрация, прогресс, статистика и окно подробностей;
- `virtual-table.js` — виртуализированная таблица результатов.

### 2. Core Layer — `src/core/engine.js`

Отвечает за организацию обработки:

- формирует очередь файлов;
- создает пул Web Worker;
- распределяет файлы между потоками;
- собирает результаты;
- рассчитывает прогресс и статистику.

Этот слой не содержит логики конкретных графических форматов.

### 3. Infrastructure / Parsing Layer — `src/infrastructure/`

Отвечает за бинарное чтение и ручной разбор файлов.

- `range-reader.js` — чтение отдельных диапазонов через `Blob.slice()`;
- `signature.js` — определение формата по сигнатуре;
- `parse-file.js` — выбор нужного парсера;
- `worker.js` — выполнение анализа вне UI-потока;
- `parsers/*.js` — отдельные ручные парсеры форматов.

## Реализация форматов

### BMP

Вручную разбираются структуры `BITMAPFILEHEADER`, `BITMAPCOREHEADER` и `BITMAPINFOHEADER`.

Из файла извлекаются:

- `bfSize`;
- `bfOffBits`;
- ширина и высота;
- `biBitCount`;
- `biCompression`;
- `biSizeImage`;
- `biXPelsPerMeter` и `biYPelsPerMeter`;
- `biClrUsed`.

По `biCompression` определяется способ хранения изображения, например `BI_RGB`, `BI_RLE8`, `BI_RLE4` или bit fields.

Для индексированных BMP учитывается палитра. Дополнительно проверяются размеры заголовков, положение пиксельных данных и минимальный ожидаемый размер несжатого растра с учетом 4-байтового выравнивания строк.

### PNG

Сначала проверяется 8-байтовая сигнатура PNG.

Затем вручную разбирается обязательный чанк `IHDR`, содержащий:

- ширину;
- высоту;
- bit depth;
- color type;
- compression method;
- filter method;
- interlace method.

Из чанка `pHYs` при его наличии вычисляется DPI. Из `PLTE` определяется информация о палитре.

Для небольших служебных чанков `IHDR`, `PLTE`, `pHYs` и `IEND` вручную вычисляется CRC-32.

Сжатые данные `IDAT` полностью не читаются: после получения метаданных парсер переходит к концу файла и проверяет наличие обязательного `IEND`.

### JPEG

После проверки маркера `SOI` (`FF D8`) файл разбирается как последовательность JPEG-маркеров и сегментов.

Парсер вручную находит:

- `SOF` — размеры изображения, количество компонентов и глубину;
- `APP0/JFIF` — DPI;
- `APP1/EXIF` — TIFF-структуру EXIF и возможное DPI;
- `DQT` — таблицы квантования;
- `SOS` — начало сжатого потока;
- `EOI` — корректное завершение JPEG.

Тип сжатия определяется по найденному `SOF`-маркеру, например Baseline DCT или Progressive DCT.

После `SOS` весь JPEG-поток не загружается. Для проверки `EOI` читается только небольшой участок в конце файла.

### GIF

Проверяется сигнатура `GIF87a` или `GIF89a`, затем читается `Logical Screen Descriptor`.

Из него получаются:

- ширина и высота canvas;
- наличие глобальной цветовой таблицы;
- размер палитры;
- color resolution.

При наличии global или local color table рассчитывается количество цветов палитры.

Также разбираются extension-блоки перед первым кадром, `Image Descriptor`, локальная палитра и `LZW Minimum Code Size`.

Полный LZW-поток не декодируется. В конце файла проверяется обязательный Trailer `0x3B`.

### TIFF

TIFF разбирается вручную по структуре IFD.

Сначала определяется порядок байтов:

- `II` — little endian;
- `MM` — big endian.

Затем проверяется TIFF magic `42`, читается смещение первого IFD и записи вида:

```text
tag / type / count / value-or-offset
```

Поддерживаются как значения, помещающиеся прямо в IFD-entry, так и значения, расположенные по отдельным offsets.

Парсер проходит цепочку IFD с защитой от зацикливания и ограничением количества директорий. Это позволяет корректно работать в том числе с многостраничными TIFF.

Из тегов извлекаются размеры, `BitsPerSample`, `Compression`, `PhotometricInterpretation`, `XResolution`, `YResolution`, `ResolutionUnit` и другие данные.

Также проверяются `StripOffsets/StripByteCounts` и `TileOffsets/TileByteCounts`.

BigTIFF с magic `43` определяется отдельно и выводится как распознанный, но неподдерживаемый вариант.

### PCX

Из фиксированного 128-байтового заголовка вручную читаются:

- manufacturer;
- version;
- encoding;
- bits per plane;
- `Xmin`, `Ymin`, `Xmax`, `Ymax`;
- горизонтальный и вертикальный DPI;
- число цветовых плоскостей;
- bytes per line;
- palette information.

Ширина и высота рассчитываются по координатам границ изображения.

Для 8-bit / 1-plane PCX проверяется стандартная 256-цветная палитра в конце файла.

Для RLE выполняется ограниченная потоковая проверка растрового потока, позволяющая обнаружить обрезанный файл без загрузки всего изображения в память.

## Быстродействие

Основная оптимизация проекта заключается в том, что приложение читает только те части файла, которые действительно нужны для получения метаданных.

Используются следующие приемы:

- `Blob.slice()` для частичного чтения;
- блоки по 64 КиБ и небольшой LRU-кэш в `RangeReader`;
- переходы по JPEG-сегментам без чтения изображения;
- переходы к TIFF-значениям по offsets;
- пропуск больших PNG `IDAT`;
- отсутствие полного GIF LZW-декодирования;
- ограниченная PCX RLE-проверка;
- несколько Web Worker для параллельной обработки;
- ограничение количества Worker максимум восемью;
- throttling обновления progress bar и таблицы;
- виртуализация таблицы результатов.

Благодаря этому обработка большого количества файлов не должна блокировать интерфейс браузера.

## Проверка поврежденных файлов

Ошибки одного файла не останавливают обработку всей папки. Некорректный файл получает статус **«Поврежден»** с описанием причины.

Проверяются, в частности:

- неверная сигнатура;
- несовпадение расширения и реального формата;
- отсутствие `IEND` у PNG;
- неверный CRC служебных PNG-чанков;
- отсутствие `EOI` у JPEG;
- отсутствие GIF Trailer;
- выход сегмента, чанка или offset за границы файла;
- некорректные размеры BMP;
- поврежденная или циклическая TIFF IFD-цепочка;
- некорректные TIFF strips/tiles;
- обрезанный PCX RLE-поток.

## Сторонние библиотеки

Для получения характеристик изображений сторонние библиотеки **не используются**.

В приложении применяются только стандартные Web API:

- `File`;
- `Blob.slice()`;
- `ArrayBuffer`;
- `Uint8Array`;
- `DataView`;
- `Worker`;
- `URL.createObjectURL()`.

`URL.createObjectURL()` используется только для отображения выбранного изображения в окне подробностей. Метаданные через него не извлекаются.
